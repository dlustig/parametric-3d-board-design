**§15 (i) intermittent failure — root cause and fix (Task 23).** Task 19 recorded test (i) failing 3/8 single-worker in chromium and webkit and attributed it to the middle-button pan. Reproduced before the fix with `--repeat-each 10 --workers=1`: chromium 3/10 failed, webkit 5/10 failed. Every chromium failure (and most webkit ones) was actually on the *next* step's Space+drag assertion (`cam4.x`, line 261), because the camera read back after the test's `setCamera` had reverted to `cam2` — the value the Ctrl+wheel zoom had produced before the middle-button drag. In-page instrumentation of every pointer/mouse/key event and every `onWheel`/`onPinch`/`onDrag` call showed the middle-button drag itself always worked (pointerdown → `first` with `buttons === 4`, five moves, pointerup → `last`, `cam3` exact), and that a `PINCH` call with `last === true` arrived ~140 ms after the Ctrl+wheel, with no input event behind it, and called `setCamera(placeAt(anchor, origin, start.zoom × movement))` again. That is use-gesture's `wheelEnd` timeout (`TimeoutStore.add('wheelEnd', …)`, default 140 ms): wheel and wheel-driven pinch have no native end event, so the library emits the unchanged state once more after the timeout. Because `onPinch` recomputes the camera absolutely from its memo, that late emission overwrote whatever the camera had become in the meantime — the middle-button pan (passing runs where it landed mid-drag were rescued by the drag's own `last`) or the test's `setCamera` (failing runs). The same emission re-delivers the last wheel event to `onWheel`, which applied its delta a second time: one plain wheel notch of 80 px panned 160 px (measured: `camera.y` −36.14 → 18.41 → 72.95 140 ms later; 18.41 expected). **A real app race, not test timing:** a user who pans (middle button, Space, Hand, wheel) within 140 ms of a Ctrl/trackpad zoom had the pan undone. **Fix** (`src/editor/input.ts`): `onWheel` and `onPinch` ignore the `last` emission, which never carries new input for either gesture (use-gesture's `wheelEnd`, `touchEnd`, `pointerEnd` and `gestureEnd` all re-emit without changing `_movement`). Test unchanged. **After:** (i) `--repeat-each 10 --workers=1` chromium 10/10, webkit 10/10 (chromium also 20/20); the plain-wheel notch pans exactly 80 px; `pnpm typecheck`, `pnpm test` (364) and `pnpm test:e2e --project=chromium` (90 passed, 21 skipped) green. Library note: `docs/decisions/2026-09-24-slice1-interaction.md` finding 9. **Regression (fix round 1):** `e2e/camera.spec.ts` (3 tests, desktop projects): one plain wheel notch pans exactly one notch after 250 ms; a `setCamera` and a middle-button pan made right after a Ctrl+wheel zoom still hold after 250 ms. With the fix reverted, all 3 fail in chromium, firefox and webkit (9/9 per engine at `--repeat-each 3`); with it, 15/15 per engine at `--repeat-each 5`. ## G9 Performance (Task 20)

**How to run:** `pnpm perf`. It builds with `vite build --mode perf --outDir dist/perf`; the test hook installs in any mode but `production`, so the build is production React plus the hook. It then runs `playwright.perf.config.ts`: `vite preview` on :4173, chromium, one worker, three repeats. `e2e/performance.spec.ts` skips unless `PERF=1`, which that config sets, so plain `pnpm test:e2e` never runs it. Each run prints one `G9 {…}` line (typical) and one `G9-worst {…}` line. Recorded values are the median of the three runs' values. `PERF_PROFILE=<path>` records a CDP CPU profile of 10 typical drag frames.

Why a production build: the suite's dev server runs development React, which is several times slower at reconciliation and overstates the renderer's share. At the end of step 7 the dev server measured 59.1 / 163.4 ms drag and 131.7 ms inspector (typical). The store deep-freezes projects outside production (Task 20 fix round 1). That includes the `perf` build, so the recorded numbers include the freeze. It freezes only new objects, so the cost is small.

**Measurement.**
- **Fixture.** `interlacePerformance()` (Fixture F at 15 × 15 cells) plus one 6 mm root band across the field at y = 201.3, painted last.
- **Typical case.** The root band is selected and dragged by mouse, one move per frame: each `page.mouse.move` is followed by a wait for the next paint. Then the test times the drag commit, an arrow nudge, and one Width keystroke on the band.
- **Worst case.**
  - Drags the repeat field itself, grabbed in cell (0, 0), so every field occurrence moves.
  - Enters the lattice motif (cell (0, 0)) and types one Width keystroke on band `p1`, so every cell's occurrence of it changes.
- **Snapping is off** for both drags. Each measured frame is also checked to change the selection's preview. With snapping on, most 2 px moves snap to the previous frame's geometry: 26 distinct of 60 in a check. Once classification is incremental (step 3), a repeated frame costs almost nothing, so snapped runs understated the median. This affected the first recording of steps 3–7, and the table below re-measures them.
- **Timing.** Every event is timed in-page:
  - `start`: at the event's capture phase on window.
  - `end`: at the bubble phase on window of the event that ends the app's handling (pointermove → mousemove for Moveable).
  - `raf`: in the next animation frame.
  - `painted`: in a task queued from that rAF, which runs after style, layout and paint.
- **Frame work** = (end − start) + (painted − raf). It is the main-thread time one drag update costs, excluding any time spent waiting for the next frame, and it is the gate metric. Plain rAF intervals can never drop below the display's refresh interval (16.7 ms at 60 Hz), so they would read about 16.7 ms for any frame that does little work.
- **Frame shown** = painted − the last rAF timestamp at or before `start`. It runs from the start of the frame the input arrived in to the paint that shows it, so it includes the wait for the next frame and is never below one refresh interval.
- **Latencies** = painted − start.
- **Assertions.** The spec asserts only its own sanity: ≥ 1000 occurrences, 60 changing frames, the expected selection, a live preview, and one history entry per commit. A missed target is a finding, not a failure.

**Profile (baseline, CDP CPU profile of 10 drag frames, dev server).**
- `findIntersections` took 93% of drag time.
- 51% was Flatten boolean polygon intersection: `booleanOpBinary` and its helpers `less_than`, `Point`, `shapes2face`, `Polygon` and `Face`. These calls came from two passes:
  - the `occluded` pass, which tested every element painted between two crossing bands with no early-out;
  - the all-pairs `crowded` pass.
- Each frame classified the whole world three times:
  - `rematchCrossings` (called by `translateObjects`) for the committed project;
  - `rematchCrossings` again for the moved project;
  - `buildScene` for the preview.

**Remedies, in the order the profile pointed to.** The packet's order after "profile" is: reduce redundant DOM, exploit reuse, then Canvas. The profile put 93% of the time in classification and almost none in the DOM, so the remedies started with classification (steps 1–5). The DOM step (6) and the reuse step (7) came after, once rendering showed up in the profile. Each step was committed and measured separately.

2. This is SPEC §6.2–§6.3's design: classification never depends on the camera, so a project's listing is cached by project reference, keeping the four most recent projects. A listing holds the occurrences and classified intersections, per context. `rematchCrossings`, `buildScene`, the unresolved markers and gesture snap targets all share it.
   - The committed project hits the cache on every frame, and the scene reuses the listing the rematch just made.
   - This is also the commit-latency remedy the brief anticipated: `rematchCrossings` no longer reclassifies `before`, and it computes `after` once for the next scene.
3. `findIntersections(occurrences, previous)` reuses a previous list's contacts for a pair when both occurrences, and every occurrence painted between them, kept their geometry. It also reuses their `crowded` results, unless a recomputed contact shares an occurrence with them. The result equals a full classification: tests compare both across six kinds of edit, and each reuse rule has a test that fails when the rule is removed.
4. Repeats the bounding-box bound in the frame of each polygon edge, using the projections on the edge direction and on its normal. For convex polygons an edge normal separates any disjoint pair. This also cuts a full classification (load, zoom, the first frame of a gesture, any whole-field edit) from about 300 ms to about 110 ms in Node.
5. Indexes records by canonical key once per record list. Computes a listing's intersection keys once and shares them between resolve, rematch, the unresolved markers and patch ordering.
6. SceneSvg keyed elements by index, so every frame re-rendered all 9146 elements, and a patch appearing mid-list rewrote every later one. Elements are now keyed by occurrence (patches by under occurrence and position) and rendered as memo components compared on geometry and colour.
7. `expand` returns the earlier occurrence object when the same source object appears at the same key under an equal matrix. Unchanged occurrences therefore keep their identity across versions, and their derived shapes (bounds, segments, painted polygons) and reused contacts are kept by identity.

No step was reverted. Canvas was not evaluated: the packet puts it last, and the brief ruled it out. The caches assume projects are never mutated in place, and outside production the store enforces that: every project it takes in is deep-frozen, so an in-place write throws.

**Where the time goes now (profiles after step 7, production build).**
- **Typical case, about 29 ms.** No single function dominates.
  - About half is in `translateObjects` → `rematchCrossings` → the new listing: `expand` walks all 3151 occurrences with their key strings, the classification runs incrementally, and the listing's keys are rebuilt.
  - The other half is in React. `buildScene` re-resolves all 3875 intersections (`resolveIntersection`, `canonicalKey`, `commonPrefix`) and builds the patch clips. SceneSvg then creates and compares 9146 memo elements.
- **Worst case, about 150 ms.** Every occurrence changes, so each frame is a full classification (about 110 ms) plus a full scene and render.

**Next steps (reviewer's follow-ups; not implemented).**
- Memoise each intersection's resolution by identity: step 7 keeps unchanged intersections' objects, so `buildScene` can skip re-resolving them.
- Memoise patch elements by intersection and clip, so an unchanged patch's clip polygon and element are not rebuilt.
- Reuse repeat-cell subtrees in `expand`, so a frame does not re-walk 3150 occurrences to move one. For the worst case (the whole field moving), a translated field could also reuse its cells' classification shifted by the delta, instead of reclassifying.
